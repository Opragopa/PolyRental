# PolyRental Mini App — Website Audit

> Дата аудита: 25 октября 2026
> Аудитор: UX, контент и технический QA
> Проверенные URL: публичный `/miniapp`, `/miniapp?preview=1`, `/login`, `/privacy`, `/terms`, `/robots.txt`
> Режим: live production через HTTPS; заявки и документы не отправлялись

## Executive Summary

Основной путь бронирования понятен: даты и время → оборудование → контакты → проверка заказа. Живой HTTPS-адрес открывается, production-режим корректно блокирует бронирование без Telegram `initData`, а preview-flow проходит до финальной проверки без отправки заявки. На мобильной ширине iPhone 16 Pro Max элементы не выходят за границы экрана, нижняя панель действий остаётся доступной, а количество оборудования меняется предсказуемо.

Главные риски перед запуском — отсутствие публичных служебных страниц `/privacy`, `/terms` и `/robots.txt`, ограниченная проверка без реального Telegram `initData`, отсутствие полноценного состояния ошибок в интерфейсе для недоступного оборудования и слабая доступность фотографий каталога из-за пустого `alt`. Для рабочего Telegram-сценария необходим отдельный тест с реальным Telegram `initData`, ролями администратора и заявкой в базе.

## Critical Issues

Критических блокеров в просмотренном preview-flow не найдено.

## Content & Copy Issues

### 🟡 IMPORTANT — Preview-текст виден как продуктовый баннер

Текст «Демонстрация интерфейса: можно пройти шаги, но заявка не отправляется» корректен для preview, но не должен попадать в production-ссылку Mini App.

Решение: показывать его только при `preview=1`, что уже реализовано; перед запуском проверить, что в Telegram URL этот параметр отсутствует.

### 🟢 NICE TO HAVE — Уточнить ценовую единицу

В карточках цена показывается как «₽ / час», а итоговая сумма считается за период. Это корректно технически, но рядом с итогом стоит явно писать «за выбранный период», чтобы пользователь не воспринимал итог как цену за сутки.

## UX & Structure Issues

### 🟡 IMPORTANT — Нет явного объяснения этапов после заявки

Статусы показываются в личном кабинете, но до отправки заявки пользователь не видит короткого объяснения процесса: документы → проверка оператора → комплектация → выдача.

Решение: добавить компактный блок «Что будет дальше» на экране проверки заказа.

Рекомендуемый текст:

> После заявки менеджер подтвердит бронь. Затем клиент заполнит документы, оператор их проверит, и только после этого начнётся комплектация оборудования.

### 🟢 NICE TO HAVE — Недоступность оборудования

В preview все позиции свободны. Не удалось визуально пройти ветку «нет свободных экземпляров» без изменения данных.

Решение для production-проверки: показать рядом с недоступной позицией ближайшую доступную дату или кнопку «Выбрать другой срок».

### 🟢 NICE TO HAVE — Длинные списки оборудования

Текущий двухколоночный каталог хорошо работает на проверенной ширине. Для большого каталога потребуется поиск или фильтрация по категории, иначе пользователь будет долго прокручивать список.

## Conversion Issues

### 🟡 IMPORTANT — CTA понятны, но нет раннего доверительного сигнала

Кнопки «Показать оборудование», «Продолжить», «Проверить заказ» и «Подтвердить бронирование» однозначны. До финального подтверждения полезно показать короткие правила: аренда бесплатная для доверенных лиц, документы нужны для акта, серийные номера появляются только в акте.

### 🟢 NICE TO HAVE — Подсказка по сроку удержания

Удержание на 30 минут объяснено после выбора дат и на экране проверки. Рекомендуется выделить это как отдельную строку рядом с финальной кнопкой, чтобы пользователь заметил ограничение до подтверждения.

## Visual & Creative Direction

- Иерархия сильная: заголовок, шаги, карточка текущего шага и фиксированная нижняя CTA-панель.
- Цвет статусов не используется единолично и сопровождается текстом.
- Карточки оборудования достаточно контрастны, элементы количества визуально понятны.
- На узком экране проверка границ показала `scrollWidth = bodyWidth`, выходящих за viewport элементов нет.
- Для изображений каталога используется пустой `alt`, что снижает доступность для скринридеров.

## Technical Issues

### 🔴 CRITICAL — Публичные служебные URL возвращают JSON 404

На работающем домене `/login`, `/privacy`, `/terms` и `/robots.txt` возвращают `{"detail":"Not Found"}`. Если эти URL используются в политике обработки ПД, ссылках из Telegram или проверках поисковых роботов, пользователь получает техническую ошибку вместо документа.

Решение: либо добавить реальные страницы/файлы, либо убрать ссылки на несуществующие маршруты. Для ПД минимум нужен доступный операторский текст политики и отдельное согласие в Mini App.

### 🟡 IMPORTANT — Пустой alt у фото оборудования

В `app/miniapp_static/app.js` фотографии каталога создаются с `alt=""`. Для контентных фото лучше использовать название артикула.

Рекомендуемая замена:

```js
alt="Фото: ${escapeHtml(item.name)}"
```

### 🟡 IMPORTANT — Нет meta description

В `index.html` есть `viewport`, `theme-color` и `title`, но нет `meta name="description"`. Для Telegram Mini App это не блокер, но это базовый технический недочёт страницы.

Рекомендуемая строка:

```html
<meta name="description" content="Бронирование фото- и видеотехники PolyRental">
```

### 🟢 NICE TO HAVE — Open Graph

Если URL Mini App открывается вне Telegram, отсутствуют Open Graph-метаданные для предпросмотра ссылки.
