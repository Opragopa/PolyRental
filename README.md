# PolyRental

Telegram-бот и ролевая Mini App для аренды оборудования. Клиент выбирает артикулы и количество, а конкретные экземпляры назначаются при подготовке. Время клиента — Europe/Moscow. Ожидающие заявки не резервируют оборудование; доступность повторно проверяется при подтверждении. Буфер после возврата не применяется.

Версия исходного кода — **0.5.2-hotfix-1**. Отчёт для предыдущего выпуска: [0.4.6](docs/releases/v0.4.6.md). Проверки production фиксируются отдельно: [готовность выпуска 0.4.0](docs/releases/v0.4.0-readiness.md). Версия задаётся в `VERSION`, отображается в настройках профиля Mini App и возвращается в `/health`; ею же помечаются URL JS/CSS для обновления кеша. Изменения собраны в [CHANGELOG](CHANGELOG.md), решения — в [ADR v0.3.1](docs/adr/0002-v0.3.1-request-review.md) и [ADR v0.3.0](docs/adr/0001-v0.3.0.md).

Стратегия роста БД и хранения вложений описана в [docs/storage-and-retention.md](docs/storage-and-retention.md).

Для адресных подсказок анкеты задайте `DADATA_API_KEY` в серверном `.env`. Ключ хранится только на сервере; при его отсутствии адрес остаётся доступен для ручного ввода.

## Запуск

1. Скопируйте `.env.example` в `.env`. Укажите `BOT_TOKEN`, `BOT_USERNAME`, `ADMIN_IDS`, отдельный список `PII_ADMIN_IDS`, надёжные разные `SESSION_SECRET` и `ICAL_TOKEN`, публичный HTTPS `PUBLIC_URL` и параметры оператора ПД. `PII_MASTER_KEY` — случайный 32-байтный ключ в base64url; его нельзя хранить в Git или терять. В @BotFather настройте домен и Main Mini App на `PUBLIC_URL/miniapp`.
2. Для режима **бот + Mini App без панели сайта** выполните `docker compose -f compose.yaml -f compose.miniapp.yaml up -d --build`. Mini App доступна по `/miniapp`, проверка готовности — `/health`; сервис панели `web` в этом режиме не запускается. Если ранее был запущен `web` на порту 8000, остановите его командой `docker compose stop web`. Журналы: `docker compose -f compose.yaml -f compose.miniapp.yaml logs -f miniapp bot`.
   Для старого режима с панелью используйте `docker compose up -d --build db web bot`; панель доступна по `/login`.
   В управляемом облаке Codex используйте `BUILDX_CONFIG=/workspace/.buildx docker compose -f compose.yaml -f compose.cloud.yaml up -d --build db web`; файл `compose.cloud.yaml` передает CA прокси только на шаг установки пакетов.
3. Основное управление находится во вкладке «Управление» Mini App: заказы, комплектование, проверки, возврат, каталог и ремонт. Старые `/add` и `/set` сохранены как временный резерв. Команды `/confirm`, `/prepare`, `/ready`, `/issue`, `/checkin`, `/return` подчиняются тем же статусным ограничениям.

При начале подготовки заявка закрепляется за оператором до завершения; истечение 10-минутного мягкого лока не снимает назначение. Менеджер явно передаёт заявку другому сотруднику. Выдачу после подтверждения клиента может оформить текущий сотрудник; при возврате сотрудник завершает заявку после подтверждения клиента и проверки техники. Ожидающая заявка не резервирует технику и не истекает автоматически.

### Вход клиентов на сайте

Клиентский сайт доступен по `/site`: вход выполняется только через Telegram и использует тот же Telegram ID, что и Mini App. Для виджета задайте `BOT_TOKEN`, `BOT_USERNAME`, публичный HTTPS `PUBLIC_URL` и уникальный случайный `SESSION_SECRET` длиной не менее 32 символов; привяжите домен к боту в BotFather. Чтобы бот мог присылать уведомления, пользователь должен начать с ним диалог. Сессия сайта действует 24 часа; кнопка «Выйти» удаляет её с устройства. Проверку входа и отправки уведомления нужно выполнить с реальным Telegram-аккаунтом после настройки домена.

### Проверка заявки и анкеты

В «Управление → Заказы» список показывает компактные карточки со статусом, клиентом и сроком. Нажмите карточку, чтобы раскрыть её на месте: сводка, персональные данные, документы, результат проверки, действия по заказу и история разделены на блоки. После действия сохраняются выбранная заявка и положение списка. Закрытие карточки убирает загруженные реквизиты из интерфейса; для повторного просмотра нужен новый авторизованный запрос.

Обычный оператор видит статус анкеты и историю действий. Только `PII_ADMIN_IDS` могут открыть анкету, раскрыть реквизиты, посмотреть фотографии и предварительные вердикты, подтвердить документы или вернуть поля и фотографии на исправление. «Отклонить / исправить» использует существующий статус `needs_changes`: клиент получает возможность исправить анкету; отдельный окончательный отказ в анкете не вводится. Для отмены аренды используется отдельное действие заказа.

Следующий шаг соответствует существующей цепочке `pending → confirmed → preparing → ready → issued → return_inspection → returned`. Подготовка требует проверенной анкеты, готовность — проверенных экземпляров и элементов комплекта, выдача — подтверждения получателя и действия сотрудника, возврат — подтверждения получателя и проверки фактически выданных элементов. Фактические сотрудники сохраняются при выдаче и возврате; бумажная расписка содержит поля для их ручного заполнения. Сервер повторно проверяет права, состояние и блокировку при каждом действии. Карточка показывает держателя этапа и срок блокировки по МСК, а после истечения — возможность продолжить обработку. Состояние другого оператора обновляется при повторном открытии/обновлении списка; разрешение сервера остаётся окончательным.

`GET /api/miniapp/admin/bookings/{id}/history` доступен сотрудникам и объединяет разрешённые события из `audit` и `pii_audit`: действие, Telegram ID участника и время. В историю не попадают ФИО, контакты, комментарии проверки, выбранные поля, содержимое/фото документов, результаты OCR и события раскрытия/скачивания ПД. Для старых заявок доступны только ранее записанные события; история не восстанавливается задним числом. Новых миграций и переменных окружения в v0.3.1 нет.

### Подписка Google Calendar

Оператор откроет в «Управление» блок «Подписка Google Calendar», получит и скопирует защищённую ссылку, затем в Google Calendar выберет «Другие календари → Добавить по URL» и вставит её. Лента содержит подтверждённые аренды, текущую выдачу и возвраты, не включает контакты и документы клиентов. Google обновляет подписку периодически, поэтому изменения могут появляться не сразу. Ссылка является секретом доступа к расписанию — передавайте её только тем, кому разрешён просмотр.

### Добавление оборудования

В «Управление → Каталог» сначала создаётся **артикул** — модель, которую видит клиент: SKU, название, описание, фото, категория и профиль проверки. Поля ставки и буфера сохранены для совместимости; буфер в расчёте доступности не применяется. Все сотрудники могут создать свою категорию кнопкой «Создать категорию» в каталоге или форме артикула; профиль проверки выбирается отдельно. Затем внутрь артикула добавляются **экземпляры**: серийный номер, складская ячейка, состояние. Серийные номера клиентскому API не выдаются. Артикул можно скрыть из клиентского каталога без удаления истории, экземпляр — перевести в ремонт или списать. Сейчас бронирование учитывает только явно выбранные позиции; автоматические зависимые позиции временно отключены.

Администратор может выбрать «Удалить артикул» и подтвердить действие вводом SKU. Модель и все её экземпляры исчезают из рабочего каталога и становятся недоступны для новых заявок и повторного добавления; предыдущие заявки, выдачи и ремонты сохраняются в базе. Через интерфейс восстановить удалённый артикул нельзя. Действующие заявки сохраняют состав для завершения работы с ними.

Для массового добавления откройте «Управление → Каталог → Добавить оборудование из CSV» и скачайте шаблон. Файл должен быть в UTF-8, с разделителем `;` или `,`, размером до 1 МБ и не более 500 экземпляров. Обязательные колонки: `sku`, `name`, `serial`; дополнительные поля указаны в шаблоне. Один SKU может повторяться для нескольких экземпляров. Существующий SKU разрешён при совпадении названия, а серийный номер должен быть новым. Импорт одной ошибочной строки отменяет весь файл.

Идемпотентный демонстрационный каталог можно создать командой `docker compose -f compose.yaml -f compose.miniapp.yaml exec -T miniapp python scripts/seed_test_catalog.py`. Все его SKU, названия и серийные номера начинаются с `TEST-`, поэтому их легко отличить от реальной техники и скрыть через форму артикула.

## Mini App

- Для просмотра интерфейса локально откройте `http://localhost:8000/miniapp?preview=1`. Это демонстрация с примером каталога; она не создаёт заявки.
- Реальное бронирование доступно только при открытии через Telegram по публичному HTTPS-адресу. Кнопка клавиатуры «Забронировать» предлагает inline-кнопку приложения: этот запуск и меню Telegram дают подписанный `initData` для серверной проверки роли. Старый `sendData` продолжает приниматься: бот берёт ID клиента из подтверждённого сообщения Telegram. Повторная отправка с тем же `request_id` возвращает прежнюю заявку.
- Календарь сразу виден на первом экране. Первый тап задаёт начало, второй — конец; третий начинает новый выбор. Затем выберите два времени по МСК. Доступны сброс, краткая сводка, черновик и быстрые сроки в раскрываемом блоке. Сохранено прежнее ограничение выдачи: с четвёртого календарного дня от сегодня. Буфер после возврата не применяется; выдача и приём возможны в рабочее время по МСК.
- Общий модуль `app/roles.py` определяет права бота, API и web по `ADMIN_IDS` и `PII_ADMIN_IDS`. Пустой или некорректный `ADMIN_IDS`, а также некорректный непустой `PII_ADMIN_IDS` останавливают запуск. PII-администратор также получает служебный интерфейс. Администратор попадает в «Управление» при открытии, вкладка «Как клиент» позволяет явно перейти к бронированию. Изменение ID требует перезапуска backend/бота, клиент пересобирать не нужно. Журнал `polyrental.access` содержит только ID, UTC-время и точку входа.
- `DOCUMENT_CHECK_MODE=local` включает Pillow и локальный Tesseract (`rus+eng`, включён в Docker). Предварительный результат «документ / не документ / не определено» и «студенческий / другой / не определено» вместе с причиной зашифрован AES-256-GCM и виден PII-администратору в ревью. Ни фото, ни распознанный текст не передаются наружу. Нечёткий кадр, не-документ, другой документ, таймаут и сбой остаются на ручной проверке. `DOCUMENT_CHECK_MODE=manual` отключает автоматическую классификацию. Для запуска без Docker установите Tesseract и языки `rus`/`eng`; при его отсутствии работает ручной fallback. Обновите `PRIVACY_POLICY_VERSION` до новой версии согласия, например `2026-10-30-v4`.
- Mini App хранит на устройстве черновик сроков и выбранного оборудования, а также последние имя и контакт для следующей заявки. Фото анкеты временно сохраняются на устройстве до отправки, максимум на 24 часа; реквизиты анкеты в локальный черновик не входят. Отправленная заявка ожидает решения без срока истечения, но не резервирует оборудование до подтверждения.
- После подтверждения заказа клиент отдельно принимает согласие и заполняет защищённую анкету. Изображения нормализуются без EXIF, а анкета и файлы шифруются AES-256-GCM отдельным ключом. Обычные `ADMIN_IDS` не имеют доступа к полным данным.
- В локальном режиме с `PUBLIC_URL=http://localhost:8000` кнопка бота запускает оформление в чате. Telegram Mini App требует публичного HTTPS-адреса, направленного на сервис `miniapp`, и настройки URL в @BotFather. Адрес `localhost` нельзя открыть из Telegram у других пользователей.

### Публикация через Nginx

Для домена `polyrental.cloudopragopa.online` подготовлен Compose-файл `compose.public.yaml`. Из-за уже работающего в Windows Nginx контейнер проекта использует локальные порты 8080 и 8443; сам Mini App доступен напрямую только с этого компьютера по `127.0.0.1:8000`. Панель сайта `web` при таком запуске не включается.

1. Убедитесь, что A-запись домена указывает на внешний IP компьютера или маршрутизатора. На маршрутизаторе создайте правила TCP: внешний порт 80 → `192.168.1.161:8080`, внешний порт 443 → `192.168.1.161:8443`. Разрешите локальные порты 8080 и 8443 в брандмауэре. Для выпуска сертификата путь `http://polyrental.cloudopragopa.online/.well-known/acme-challenge/` должен быть доступен из интернета на стандартном порту 80.
2. Запустите `docker compose -f compose.yaml -f compose.miniapp.yaml -f compose.public.yaml up -d --build db bot miniapp nginx`. До получения сертификата Nginx отдаёт на обычные запросы HTTP 503; путь проверки домена уже работает.
3. После обновления DNS из папки `C:\PROJECTS\PolyRental` выполните `powershell -ExecutionPolicy Bypass -File .\scripts\enable-https.ps1 -Email you@example.com`, подставив свой адрес для уведомлений Let's Encrypt. Из любой другой папки укажите полный путь `C:\PROJECTS\PolyRental\scripts\enable-https.ps1`. Скрипт получает сертификат, проверяет конфигурацию Nginx, включает HTTPS, записывает `PUBLIC_URL=https://polyrental.cloudopragopa.online` в `.env` и пересоздаёт бота и Mini App.
4. Проверьте `https://polyrental.cloudopragopa.online/health` и `https://polyrental.cloudopragopa.online/miniapp`. В @BotFather задайте URL Mini App `https://polyrental.cloudopragopa.online/miniapp`.

Сертификат необходимо продлевать. Запускайте `powershell -ExecutionPolicy Bypass -File .\scripts\renew-certificate.ps1` по расписанию, например раз в месяц; команда проверяет срок сертификата и перезагружает Nginx.

Новые акты не формируются. В готовности создаётся DOCX по старому шаблону для скачивания и печати; при выдаче он атомарно включается в неизменяемый архив на пять лет. Клиент видит только свою расписку; полные документы сотрудников и исторические DOCX доступны только `PII_ADMIN_IDS`. Ранее сохранённые PDF остаются доступными в исходном формате. Старые файлы не перезаписываются. Логические подтверждения Mini App не заменяют бумажные подписи.

Redis — необязательный внутренний кэш публичного каталога, категорий и расписания. Compose запускает `redis:7-alpine` без публикации порта и без сохранения данных на диск; предел памяти — 128 МБ. `REDIS_URL` можно переопределить для доверенного Redis. Перед включением кэша примените миграции; штатный deploy запускает Redis отдельно. Ключи доступны только внутри сети Compose, результаты доступности живут до 5 секунд, категории и расписание — до 5 минут. Изменения оборудования, броней и категорий меняют ревизию кэша в той же транзакции PostgreSQL. Если Redis или таблица ревизии недоступны, приложение обращается напрямую к базе; создание заявки всегда повторно проверяет доступность в PostgreSQL. Для отката достаточно вернуть предыдущий образ приложения: данные Redis не являются источником истины.

Миграции: `alembic upgrade head`. При первом запуске также выполняется совместимый backfill: старые экземпляры группируются только при полном совпадении названия, ставки, описания и изображения; старые брони получают строки и уже назначенные экземпляры.

Сбор документов не включится, пока не заданы `OPERATOR_NAME`, `OPERATOR_ADDRESS`, `OPERATOR_CONTACT`, `PRIVACY_POLICY_VERSION`, `PII_ADMIN_IDS` и `PII_MASTER_KEY`. База и резервные копии с ПД должны физически размещаться в РФ; техническая реализация не заменяет юридическое утверждение политики и согласия.

Зашифрованная резервная копия без промежуточного plaintext-файла: задайте отдельный `BACKUP_MASTER_KEY` и выполните `python scripts/backup_encrypted.py D:\PolyRentalBackups`. Скрипт шифрует поток `pg_dump` через AES-256-GCM и удаляет зашифрованные копии старше 30 дней. Ключ храните отдельно от копий и рабочей базы.

Тесты: `docker compose --profile test run --rm --build test`. Compose создаёт для них отдельную БД `polyrental_test`, применяет Alembic-миграции и запускает pytest. UI и unit-тесты календаря описаны в [стратегии тестирования](docs/testing-strategy.md). CI проверяет Python, Chromium, WebKit и синтетический benchmark документов перед deployment. [Отчёт приёмки](docs/qa/v0.3.0-acceptance.md) отделяет автоматические результаты от проверки физического iPhone и точности на реальных документах.

### CI/CD

GitHub Actions запускает тесты для pull request и каждого push. Deployment после успешного push в `main` выполняет self-hosted runner на production Windows-хосте: входящий SSH и роутерный проброс не нужны. Установите runner с меткой `PolyRental` от имени пользователя, у которого есть доступ к Docker, `.env` и read-only Deploy key для `git pull`. В GitHub Actions Variables добавьте `DEPLOY_PATH` (абсолютный путь к production-клону, например `C:\PROJECTS\PolyRental`) и `DEPLOY_ENABLED=true`; пока флажок не включён, deployment-job будет пропущен, а CI продолжит проверять код.

Адаптированная [стратегия тестирования Mini App](docs/testing-strategy.md): локальный preview, API и роли, эмуляция Telegram, реальные клиенты и проверка удобства пользователями.

Практическая [отладка Telegram Mini App](docs/telegram-debug-report.md) и [запуск локальных инструментов](tools/telegram-qa/README.md): Vite-панель, проверка подписей, tg-mini-app-emulator и DevKit. Для отдельного тестового сервера Telegram предусмотрен `TELEGRAM_TEST_ENVIRONMENT=1`; в обычном окружении оставляйте `0`.

### Структурированные названия каталога

Исходное полное название модели сохраняется в `name`; отдельные поля `kind`,
`brand` и `key_spec` сохраняются как отдельные характеристики. Заголовок карточки всегда использует полное `name`. Администратор может
исправить их в карточке артикула. Изменения полей названия и категории через
Mini App записываются в `article_title_audit` с идентификатором оператора.
Структурированные поля не сокращают название в каталоге. Миграция
заполняет поля по локальным правилам и не изменяет исходное название.

Основная характеристика зависит от вида: карта памяти и накопитель — объём;
аккумулятор — ёмкость или энергия; объектив — фокусное расстояние; штатив —
высота. Для камеры и остальных видов характеристику можно указать вручную.
Автоматическое распознавание приблизительное, поэтому результат следует
проверить при редактировании каталога.

### Профиль и инструкция

Проверенный Telegram ID определяет профиль. Клиент попадает на выбор дат,
оператор — в управление; оператор может перейти в бронирование и вернуться к
последнему открытому разделу управления, сохранённому на сервере между устройствами. Первый вход в
бронирование показывает четырёхэкранную инструкцию, которую можно пропустить
или повторно открыть в профиле. Отметки первого показа и завершения хранятся
на сервере; историю заявок можно фильтровать и просматривать страницами.
Дата вступления определяется по первой известной заявке либо первому созданию
профиля. Поддержка доступна из профиля и карточек заявок; право клиента на бронирование проверяется сервером отдельно от статуса проверки личности.
Настройка необязательных напоминаний сохраняется сервером отдельно для каждого
пользователя. Напоминания о выдаче и возврате отправляются за сутки и за два часа; при отключении ещё не отправленные напоминания отменяются. Важные сообщения по заявкам не зависят от этой настройки.

Праздники для расчёта SLA задаются через `SLA_HOLIDAYS` как даты
`YYYY-MM-DD`, разделённые запятыми; по умолчанию список пуст. Этот календарь
независим от `NON_WORKING_DATES` и `WORKING_DATES`, которые относятся к выдаче
и возврату. SLA использует рабочее время Москвы: будни 09:00–17:30, летом 08:30–17:00; взятие заявки — 2 рабочих часа, выполнение — 24. Для эскалаций в общий Telegram-чат задайте `SLA_SHARED_CHAT_ID` и добавьте в него бота. Пока ID не задан, доставка в общий чат отключена.

### v0.4: выдача, исправления и рабочий календарь

«Управление → Сотрудники» позволяет администратору назначить подроль ID из `ADMIN_IDS` и включить сотрудника в доверенный список с ФИО. Роли наследуются: admin → manager → operator. `PII_ADMIN_IDS` проверяется независимо. ID только из PII-списка получает ревью документов, но не складские полномочия.

Менеджер редактирует даты/состав с diff и ответом клиента, запрашивает исправления или отклоняет заявку с обязательной причиной. Ответ на `manager_edit` ожидается 24 часа; за два часа приходит напоминание, затем заявка возвращается в `pending` с отметкой «клиент не ответил». Причины и комментарии зашифрованы и отсутствуют в общей истории.

Комплектация модели задаётся по одному элементу на строку. При подготовке сотрудник отмечает невыданные/заменённые экземпляры и элементы. Клиент подтверждает список исключений; он включён в приложение DOCX-расписки; исторические PDF доступны без изменения. Возврат проверяет фактически выданное. Особенности берутся из снимка выдачи; поздние изменения карточки его не меняют. Изменения до выдачи требуют повторной подготовки.

Плановые даты выдачи и приёма выбираются по рабочему календарю: будни 09:00–17:30 МСК, июнь–август 08:30–17:00, с `NON_WORKING_DATES` / `WORKING_DATES`. Ограничение начала `today + 3` действует дополнительно. Фактические действия сотрудников и подтверждение сдачи клиентом доступны круглосуточно. `ENFORCE_HANDOVER_SCHEDULE` ограничивает плановые даты и включён по умолчанию; выключение допустимо для контролируемого отката старого потока.

В карточке экземпляра можно указать владельца/контакт и внешнюю занятость на срок с публичной причиной. Внешняя занятость конкурирует с бронированием под той же блокировкой доступности. При ущербе/утере сотрудник получает контакт владельца; само имя владельца не влияет на доступность и не попадает в юридические реквизиты расписки.

Перед обновлением выполнить `alembic upgrade head`, проверить backup и восстановление вне рабочей БД. Новые миграции — `20261029_30`–`20261030_33`. Backfill номеров резервирует диапазоны короткими операциями над годовыми счётчиками; сканирование не удерживает табличную блокировку. Короткие DDL-блокировки неизбежны. Исторические записи упорядочены внутри года; новые заявки во время backfill могут получать номера до завершения исторического заполнения.

Проверка зашифрованного backup с реальным восстановлением только в `db_test`: `python scripts/verify_test_restore.py --seed-synthetic --fresh-migrations`. Команда добавляет синтетические данные только в `polyrental_test`, создаёт и удаляет отдельные проверочные БД. Production не используется.

Подробности: [состояние реализации](docs/design/v0.4.0-status.md), [приёмка](docs/qa/v0.4.0-acceptance.md), [поэтапный выпуск](docs/design/rollout-v0.4.md).

Фото модели загружается из управления каталогом: JPEG/PNG/WebP до 8 МБ, сервер сохраняет WebP до 640×640 и 100 КБ без EXIF в PostgreSQL и включает его в JSON каталога. Загрузку можно заменить или удалить; HTTPS-ссылка остаётся резервным вариантом.

Контроль хранения: `python scripts/check_storage.py BACKUP_DIRECTORY` при доступной `DATABASE_URL`. Команда читает размеры БД/таблиц, суммарный размер и возраст последней зашифрованной копии, возвращает JSON и код 1 при превышении порога. Пороги — `DATABASE_WARN_GIB=5`, `BACKUP_WARN_GIB=50`, `BACKUP_MAX_AGE_HOURS=26`; их следует согласовать с выделенным диском. Подробности — [хранение](docs/storage-and-retention.md).

Единый [чек-лист приёмки Telegram Mini App](docs/qa/miniapp-acceptance.md) содержит критерии, доказательства и границы проверок. [Проверка на устройствах](docs/qa/miniapp-device-session-2026-11-01.md) заполняется по фактическому прохождению iPhone/Android/Desktop.

### Окно обновлений

Обычный выпуск добавляется в `app/assets/releases.json`: версия, дата, короткие пользовательские изменения и аудитория (`all` / `staff`). Mini App показывает их при входе после инструкции первого запуска. Закрытие окна или переход к предложению записывает `release_seen:X.Y.Z` в активность аккаунта; повторный вход с другого устройства не вызывает показ. Hotfix использует ключ обычного релиза: новых уведомлений для уже ознакомившихся нет, пропустивший основной выпуск может прочитать его изменения. Для версии без подготовленного описания окно не показывается.

«Помогите нам стать лучше» открывает форму существующей поддержки. Предложение помечается в зашифрованном сообщении; доступ сотрудников к переписке не расширяется. Благодарность показывается только после успешного сохранения. Миграции и дополнительные переменные окружения для этого не требуются.

### Публикация релизов в Telegram-канале

`RELEASE_CHANNEL` задаёт ID канала или его `@username`. Бот должен быть администратором с правом публикации. Обычный релиз берёт все пункты из `app/assets/releases.json`, включая аудиторию сотрудников; поля `previous_version` и `emoji` нужны для поста по формату release notes. Этот же список используется в окне «Что нового».

После запуска Mini App worker публикует текущий обычный релиз. Таблица `release_publications` хранит уникальную пару «ID канала + версия», снимок текста и номер сообщения. Перезапуск и параллельный worker не создают второй пост. Hotfix не создаёт публикацию, но может завершить уже ожидающий пост основного релиза. Явный отказ Telegram повторяется позже. При таймауте/обрыве с неизвестным результатом автоматическая повторная отправка отключается (`uncertain`): сначала нужно проверить канал, поскольку Telegram не поддерживает ключ идемпотентности для `sendMessage`.

Перед первым запуском этой возможности применяется миграция `20261105_41`. Откат приложения не требует удаления журнала публикаций.
