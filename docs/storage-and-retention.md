# Хранение данных и рост базы

## Решение сейчас

Оставить заявки, аренду, оборудование, проверки и связи между ними в одной PostgreSQL. Эти данные часто меняются вместе и связаны внешними ключами; разделение по разным базам усложнит транзакции, удаление заявки, резервное копирование и восстановление. Несколько баз на том же диске сами по себе не уменьшают общий объём хранения.

Самый объёмный тип данных — фотографии анкеты: они хранятся в БД зашифрованными, а общий размер одного комплекта ограничен 32 МБ. Фото удаляются по срокам хранения анкеты: через 24 часа после отмены/истечения заявки и через 90 дней после завершения аренды или ремонта. Новая PDF-расписка и отдельная зашифрованная копия получателя хранятся пять лет независимо от удаления анкеты; затем байты удаляются, остаются минимальные факты выдачи/приёма. Старые акты сохраняются в PII-архиве и заново не создаются.

Пока активная аренда не завершена и в течение срока хранения после возврата, клиент может автоматически подставить реквизиты и фотографии из своей последней анкеты в новую форму. Пользователь может заменить любое фото новым; новое изображение заменяет старое для этого документа. Согласие на обработку запрашивается для каждой новой заявки.

Грубая верхняя оценка показывает, почему вложения надо контролировать: 100 анкет в день по 32 МБ при сроке 90 дней — до 281 ГиБ только на фото, без индексов и резервных копий. Это заведомо worst case; нужно измерить фактический средний размер комплекта. До роста нагрузки настроить оповещение о заполнении диска PostgreSQL и резервных копиях. Планировать вынос файлов в объектное хранилище при достижении 20 ГБ вложений или 30% выделенного диска — что наступит раньше.

## Что уже ограничивает рост

- Фото и анкета шифруются; автоматическая очистка действует по срокам из `app/pii.py`.
- Удаление заявки сохраняет обязательный пятилетний архив расписки; состав удаляемых операционных данных и прав проверяется сервером.
- Для контроля самого факта удаления остаётся маленькая запись без данных клиента: номер удалённой заявки, ID оператора и время.
- Номер расписки имеет вид `ТС-ГГNNNN`: `ГГ` — год оформления, `NNNN` — уникальный номер заявки с ведущими нулями. Номер хранится в заявке и не меняется при повторном скачивании документа.

## Когда выносить файлы отдельно

Не создавать отдельную базу для фотографий. Когда объём зашифрованных вложений или стоимость резервных копий начнёт мешать эксплуатации, вынести байты файлов в шифрованное S3-совместимое хранилище с lifecycle-правилами, а в PostgreSQL оставить booking ID, тип файла, размер, контрольную сумму и ключ объекта. Срок удаления должен задаваться централизованно и удалять объект вместе с записью анкеты.

Отдельный сервер или кластер PostgreSQL рассматривать только при измеренном ограничении по нагрузке, доступности или обслуживанию. Архивирование старых заявок и партиционирование аудита — после оценки реального роста и требований к срокам хранения. До этого достаточно мониторить свободное место, размер крупных таблиц и объём резервных копий, а также регулярно проверять восстановление бэкапа.

## Реализованный контроль v0.4

`python scripts/check_storage.py BACKUP_DIRECTORY` использует `DATABASE_URL`, только читает БД и метаданные файлов `polyrental-*.prbak`. Вывод — JSON без содержимого заявок; код 0 означает пороги не превышены, 1 — предупреждение, ошибка подключения/пути также даёт ненулевой код. Проверяются размер БД (по умолчанию 5 ГиБ), сумма копий (50 ГиБ), отсутствие или возраст последней копии (26 часов). Настройки: `DATABASE_WARN_GIB`, `BACKUP_WARN_GIB`, `BACKUP_MAX_AGE_HOURS` либо аргументы CLI.

При выкладке подключить команду к существующему мониторингу/планировщику после ежедневного backup и направить ненулевой код в штатные оповещения. Сам скрипт ничего не отправляет в Telegram. Свободный диск контролирует мониторинг хоста; успешная проверка размера не подтверждает целостность копии — для этого предусмотрено отдельное восстановление.

Отчёт включает двадцать крупнейших таблиц и `partition_review=true`, если таблица аудита достигла 1 ГиБ. Это порог для измерения скорости роста и плана партиционирования, без автоматического изменения/переноса данных. Объектное хранилище остаётся условным следующим этапом при достижении 20 ГБ вложений или 30% диска; инфраструктуру и ключи выбирают по фактической среде.

Фото моделей хранятся отдельно в `article_images`: до 640×640, максимум 100 КБ WebP без EXIF, одна запись на модель. Клиент получает миниатюру прямо в ответе каталога, без отдельного запроса на изображение. Исходный файл не хранится. Миниатюра публична как часть каталога и не предназначена для документов клиента.
