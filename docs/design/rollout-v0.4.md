# PolyRental v0.4 — выпуск кандидата и production

**Исторический план RC.** На 01.11.2026 рабочая версия подтверждена как 0.4.5, локально подготовлена 0.4.6. Для ближайшего выпуска использовать [инструкцию 0.4.6](../releases/v0.4.6.md) и [ROADMAP](../../ROADMAP.md). Старые указания об обязательном подписанте, формате новых PDF и создании финального тега 0.4.0 не являются текущими целями.

Кандидат: `0.4.0-rc.1`. Код и миграции подготовлены совместно. Финальный тег v0.4.0 создаётся после внешней приёмки. Workflow сохраняет явный переключатель `DEPLOY_ENABLED=true`; локальная проверка не означает включение production deployment.

## До переключения

1. Зафиксировать SHA/версию работающих образов, миграцию БД, количество активных заявок по статусам и конфигурацию без секретов в логах.
2. Сохранить проверенный зашифрованный production backup и отдельно ключи. Проверить реальное восстановление в отдельную БД, сохранить прежние образы. Тестовая команда `verify_test_restore.py` проверяет только синтетическую db_test.
3. На выбранном коммите выполнить полный CI: сервер, Chromium/WebKit, документы и тестовое восстановление. Реальные iOS/Android/Desktop проверить на staging с синтетическими анкетами и доступными операторами.
4. Назначить подроли, доверенных подписантов и PII-проверяющих. Установить новую версию согласия и проверить календарные исключения учреждения.

## Переключение

1. Приостановить запись, применить `alembic upgrade head` до 20261030_33 и обновить backend, бот и Mini App совместно. Не оставлять старых писателей, которые не знают о внешней занятости и подтверждениях.
2. Проверить /health, серверные права и новый полный цикл, восстановление после ошибок и одновременное подтверждение. Возобновить запись после успешной проверки.
3. Старые ready вернуть в подготовку для новой расписки. Для старых issued/return_inspection использовать отдельный перенос через PII-сотрудника с подролью. Снимок прошлого неизвестен, подписи не выдумываются; старые DOCX/акты сохранены.
4. Проверить доставку бота/SLA, возврат старой заявки, клиентское скачивание и Google Calendar. Записать результаты и известные ограничения. После этого заменить RC финальной версией и создать тег на проверенный SHA.

## Откат

Остановить запись, сохранить новые события и оценить совместимость данных. Аддитивные таблицы 30–33 при downgrade сохраняются, однако старый код не применяет их правила. Восстановление backup перезапишет новые операции; их требуется перенести или сверить отдельно. Календарный флаг false допустим только для контролируемого старого потока. Не удалять ключи пятилетнего архива вместе с 90-дневной очисткой анкеты.

DDL PostgreSQL требует коротких блокировок. Нумерация больше не удерживает табличную блокировку на длительное сканирование; годовые диапазоны выделяются отдельными короткими операциями. На реальном объёме оценить задержки и окно DDL отдельно.
