# PolyRental v0.4.0 — состояние и оставшиеся работы

Срез: 28.10.2026. Источник требований — `requirements.md`, роли — `docs/design/roles.md`. Локальный `VERSION` по-прежнему `0.3.2`; изменения не закоммичены. Состояние production и GitHub-тега в этом проходе не проверялось. Галочка означает подтверждённое локально поведение, а не выпуск или развёртывание. Этот список — ориентир для продолжения, а не замена полной проверки каждого требования.

## Что уже подготовлено

- [x] `today + 3` по Москве при оформлении и в клиентском календаре; API доступности также проверяет срок.
- [x] `pending` / `needs_changes` не резервируют оборудование; при подтверждении доступность проверяется повторно под блокировкой. Буфер после возврата исключён из расчёта.
- [x] Удалена необратимая очистка тестовых заявок; есть скрытие и восстановление.
- [x] Восстановление завершённой заявки как черновика через «Повторить заявку» с выбором новых дат и проверкой доступности.
- [x] Базовая валидация возраста, паспортных дат и необязательного номера студенческого; поле вуза убрано из клиентской формы.
- [x] Каркас хранимой подроли и ограничение части действий в Mini App, боте и web; PII-проверка остаётся отдельной.
- [x] Обратные переходы по матрице, обязательный зашифрованный комментарий, ограничение роли и владельца этапа; повторная приёмка требует новых проверок.
- [x] Генерация PDF в памяти, отдельный зашифрованный архив и срок хранения пять лет; подготовлены клиентская выдача сохранённого PDF, одноразовая ссылка и кнопка профиля. Сохранение PDF ещё не связано с выдачей, поэтому пользовательский цикл целиком не работает.
- [x] Подписка календаря использует резервирующие статусы и содержит позиции и даты без реквизитов клиента.

## Что осталось для v0.4.0

### 1. Выдача, возврат и документы — основной блокер

- [ ] Подключить формирование и архивирование PDF к реальному процессу выдачи; обеспечить доступ клиенту и предварительный просмотр до приёмки. Зафиксировать совместимость старых активных заявок и существующих DOCX/актов.
- [ ] Исключить создание новых актов и зависимость выдачи от отметки акта; старые акты оставить в архиве только для `PII_ADMIN_IDS`, без удаления файлов.
- [ ] Реализовать доверенных сотрудников и две бумажные точки подписи с логическим подтверждением «Подписал [ФИО]»; отдельные действия «Получил», «Подтверждаю выдачу», «Личность сверена», «Сдаю оборудование» и «Личность сверена, совпадает».
- [ ] Зафиксировать получателя и неизменяемое ФИО после подтверждения; отклонять возврат другим человеком. Проверить транзакционность действий и восстановление после сбоев.
- [ ] Реализовать частичную выдачу: причины, замены, перечень, бейдж, подтверждение ознакомления и лист-приложение к расписке. При возврате проверять фактически выданные и заменённые единицы.
- [ ] Проверить пятилетнее хранение PDF вместе с текущим удалением ПД и ключей, обработкой backup и историческими документами; подтвердить, что метаданные подписания сохраняются после удаления PDF.

### 2. Инвентарь и ущерб

- [ ] Добавить необязательного владельца и контакт, правила видимости и внутреннее уведомление сотруднику при поломке/потере; не связывать поле владельца с Telegram ID и доступностью.
- [ ] Реализовать особенности экземпляра, append-only для оператора, правку/удаление админом, аудит и неизменяемый снимок на выдаче.
- [ ] На возврате сравнивать со снимком; различать ранее существовавшую черту и новый ущерб, сохранять результат в заявке. Определить и проверить сценарий старых заявок без снимка.
- [ ] Добавить компактный список замены: до 10 элементов без скролла, свыше — поиск по ID/названию.

### 3. Заявки и роли

- [ ] Реализовать `needs_changes` самой заявки и `change_type: client_fix | manager_edit`; не путать с существующим статусом проверки анкеты.
- [ ] Добавить редактирование менеджером, diff, подтверждение или оспаривание клиентом, обязательный комментарий при споре, напоминание за два часа и переход в `pending` через 24 часа без ответа. Проверить повторы и перезапуск фонового процесса.
- [ ] Довести проверку подролей до всех действий и всех входов, согласовать права на ещё не определённые операции и управление назначениями. Применять `ADMIN_IDS` для административного доступа, `role` для действия, `PII_ADMIN_IDS` для ПД. Учесть текущих пользователей только из PII-списка.
- [ ] Завершить жёсткое закрепление заявки при подготовке и согласовать его с 10-минутным локом; убрать устаревшее сообщение о свободном этапе.
- [ ] Проверить видимость и обработку зашифрованного комментария при возврате на доработку; не раскрывать ПД в общей истории.

### 4. UI, уведомления и совместимость

- [ ] Убрать со страницы выбора дат «Условия и быстрый срок» и устаревшее описание буфера; убрать ставку и цены из всех пользовательских потоков при сохранении полей модели.
- [ ] Привести кнопки и подтверждения к матрице 5.5, включая «Отменить заявку» вместо «Отменить заказ»; реализовать оверлеи этапов и сообщение о завершении оператору и клиенту.
- [ ] Довести фото и просмотр, плотность карточки, одинаковые кнопки, названия, доступность касания и адаптацию к клавиатуре до требований. Проверить, что скрытый Telegram ID нигде не показывается клиенту.
- [ ] Проверить поведение анкеты и связанных фото на старых данных, уведомление при исправлении, мобильную клавиатуру, экранные дикторы и реальные Telegram iOS/Android/Desktop.

### 5. Проверка и выпуск

- [ ] Сверить фактические версии, миграции и активные заявки production; проверить резервное копирование и восстановление, совместимость старого и нового кода и план отката для каждого этапа.
- [ ] Прогнать полную серверную и браузерную матрицу, включая конкурентные подтверждения, прямые API и сквозной цикл с синтетическими данными. Выполнить приёмку по разделу 10 `requirements.md`.
- [ ] Обновить документацию, `VERSION`, релизные записи и UI-кеш; провести проверку CI на точном коммите.
- [ ] Подготовить и выполнить поэтапный deploy, проверить production, затем создать или обновить GitHub-тег v0.4.0 на проверенный коммит. Сейчас это не выполнено.
