# v0.4.0 — кандидат

Версия подготовлена в рабочей ветке; публикация и развёртывание не выполнены.
Текущая опубликованная версия и файл `VERSION` остаются v0.3.1 до завершения
приёмки и проверки оставшихся требований.

## Изменения

- Бронирование начинается с календаря, затем открываются каталог и серверная
  корзина. Доступность проверяется повторно при отправке заявки; изменения
  рассылаются через PostgreSQL LISTEN/NOTIFY и SSE с опросом при обрыве.
- Добавлены номера ТС с годовой последовательностью, структурированные названия,
  профиль, обучение, назначение ответственного, история и поддержка.
- Удаление откладывается на пять секунд с возможностью отмены; удалённые строки
  сохраняются для восстановления. Тестовые заявки можно скрыть; необратимая
  очистка доступна через отдельную серверную операцию только администратору,
  с подтверждением номера и журналом без ПД. Допустимые причины: `test_cleanup`,
  `duplicate_test`, `invalid_test`.
- SLA считает рабочее время Москвы, исключая выходные и даты `SLA_HOLIDAYS`.
  Пустой список праздников — значение по умолчанию. При выдаче и последующем
  возврате создаётся новый цикл SLA. `SLA_SHARED_CHAT_ID` по умолчанию пуст.
- Обращения поддержки шифруются; просмотр содержимого ограничен PII-администраторами.
  Необязательные напоминания пока не отправляются; обязательные события нельзя
  отключить пользовательской настройкой.

## Проверка и ограничения

Примените миграции `alembic upgrade head` перед запуском новых процессов.
Запустите `docker compose --profile test run --rm --build test`; браузерные
проверки перечислены в `.github/workflows/ci-cd.yml`. Укажите общий чат SLA
и обеспечьте доступ бота к нему до включения эскалаций. Существующие старые
активные заявки могут сразу превысить SLA, поэтому включайте уведомления
поэтапно.

Миграция номеров перезапускается после сбоя и заполняет записи пакетами, но
на этапе резервирования ненадолго блокирует запись: строгое требование об
отсутствии блокировки пока не выполнено. В изолированной синтетической проверке
10 000 старых заявок и 180 параллельных вставок миграция заняла 0,534 с,
максимальная задержка наблюдаемой вставки составила 22 мс; это не измерение
промышленной системы. При обрыве SSE обновление зависит от восстановления
соединения или опроса с интервалом пять секунд; проверка при отправке остаётся
серверной. Возможна повторная доставка Telegram после сбоя между успешной
отправкой и фиксацией транзакции. Сквозная проверка реального Telegram и
физических устройств, промышленная нагрузка и CI для текущего коммита должны
проверяться отдельно.

## Откат

До обновления остановите запись и сделайте проверенную резервную копию БД.
Для отката остановите все пишущие процессы, сохраните данные и события,
поступившие после обновления, восстановите проверенную копию БД и прежний код,
затем согласованно перенесите необходимые новые данные. Простой откат только
кода небезопасен: старый код не учитывает новые признаки удаления и поддержки.
