# ADR 0002: проверка заявки внутри карточки (v0.3.1)

Дата: 2026-10-26. Статус: принято.

## Контекст

В v0.3.0 ревью анкеты вставлялось над списком заказов и прокручивало страницу к началу. Реквизиты раскрывались длинным абзацем, а существующие журналы статусов и PII-решений не были видны оператору в заявке.

## Решение

- На всех ширинах используем accordion внутри карточки. Одновременно выбрана одна заявка; список остаётся в документе. Отдельная двухпанельная раскладка не требуется для текущего объёма интерфейса.
- Сводка, персональные данные, документ, проверка, действия и история имеют отдельные заголовки. Полные реквизиты раскрываются явно и повторно проверяются сервером; ответы и история имеют `Cache-Control: no-store`. Загруженные реквизиты не сохраняются в браузерный черновик.
- Существующие `ADMIN_IDS`/`PII_ADMIN_IDS` остаются единственным источником прав. Оператор видит служебный статус, PII-администратор — анкету, вердикты, изображения и ручное решение.
- Сохраняем `TRANSITIONS` и все предпосылки переходов. UI объясняет следующий шаг, backend принимает окончательное решение. Ручное ревью и подпись акта сохраняют отдельные кратковременные захваты и не занимают следующий этап аренды.
- `operation_lease` остаётся прежним полем с активным захватом или `null`. Аддитивное `operation_lease_state` показывает также истёкший захват текущего этапа. Локальный таймер обновляет видимое истечение; изменение держателя другим оператором требует обновления данных. Конфликтующие записи всегда отклоняются сервером.
- История использует `Audit` и `PIIAudit`; отдельная таблица событий и миграция не нужны. Отдаём только фиксированный список действий и минимальные поля: источник/ID события, действие, категория, Telegram ID участника и время. Не отдаём произвольные audit action, события просмотра/скачивания, комментарии, поля исправления, ПД, документы или OCR. Telegram ID позволяет установить участника без дублирования ФИО в журнале.
- Старые события показываем как записано: для перехода известен новый статус, исходный статус отдельным полем ранее не сохранялся. Не создаём вымышленную историю и не обещаем юридически неизменяемый журнал.
- «Отклонить / исправить» возвращает анкету в существующий `needs_changes`. Это и есть поддерживаемый Fix. Отдельного финального отказа в анкете нет; отмена заказа остаётся самостоятельным действием.
- Автоматический результат остаётся рекомендацией. Отсутствие прежнего вердикта, отключённая проверка, сбой и таймаут показываются как необходимость ручной проверки. Шифрование AES-256-GCM, идемпотентность `request_id`, буфер и сроки аренды не меняются.

## Последствия

Обновление совместимо с v0.3.0, не меняет схему и `.env.example`. Откат выполняется возвратом образов/исходников к v0.3.0 без downgrade БД. Права, события, статус и блокировка проверяются API-тестами; размещение, темы, клавиатура, контекст и гонки UI — браузерными сценариями. Произвольные темы Telegram и реальные устройства требуют отдельной приёмки.
