## Серверные тесты локально

```powershell
docker compose --profile test run --rm --build test
```

`tests/conftest.py` разрешает тесты только для БД с именем `polyrental_test` и очищает тестовые таблицы. Не перенаправлять тесты на рабочую БД. Основной набор проверяет отсутствие резерва у `pending`/`needs_changes`, повторную доступность при подтверждении, транзакционные конфликты и идемпотентность.

Для восстановления после сборки тестового образа и запуска `db_test`:

```powershell
python -m pip install cryptography==46.0.3
python scripts/verify_test_restore.py --seed-synthetic --fresh-migrations
```

Скрипт использует только `db_test`, создаёт временные базы с отдельными префиксами и удаляет их после проверки. Ключ резервной копии генерируется на один запуск. Синтетический seed добавляет записи в `polyrental_test`; не запускать одновременно с pytest, очищающим те же таблицы.

## Браузерные сценарии

```powershell
npm ci --prefix tools/browser-qa
node --test tests/calendar.test.cjs
```

Сценарии перехватывают HTTP и читают локальные ресурсы приложения; production-сервер, Telegram-аккаунт и рабочие документы им не нужны. Для прямого запуска используйте установленный Playwright-браузер. `NODE_PATH` указывает на `tools/browser-qa/node_modules`, `PLAYWRIGHT_BROWSER` выбирает `chromium` или `webkit`. `PLAYWRIGHT_CHANNEL=msedge` применим только к Chromium и требует установленный Edge.

Воспроизведение Linux WebKit в том же образе, что в CI, из корня проекта:

```powershell
docker run --rm --ipc=host --mount "type=bind,source=$((Get-Location).Path),target=/work" --workdir /work -e NODE_PATH=/work/tools/browser-qa/node_modules -e PLAYWRIGHT_BROWSER=webkit mcr.microsoft.com/playwright:v1.62.1-noble node tests/customer-change-request-ui.cjs
```

Для Chromium замените `webkit` на `chromium`. Полный список команд находится в workflow. Версия контейнера должна совпадать с Playwright в `tools/browser-qa/package-lock.json`.

Правила сценариев: проверять результат действия и отсутствие ошибок страницы; ожидать конкретную загрузку данных/диалога, а не произвольную задержку. Для анимированных плиток отдельно проверяются обычный и reduced-motion режимы. Редактирование каталога проверяется с manager/admin; отсутствие соответствующих действий у operator также проверяется. История проверяет публичные имена и безопасный fallback, а не показ Telegram ID.

## Preview и изолированная приёмка

`/miniapp?preview=1` показывает встроенный пример без создания заявок. Текущий путь клиента: каталог → корзина → даты/время → проверка заявки. Preview не подтверждает серверные права, резервирование или доставку Telegram Update.

Для реальных API, чата бота, входа на сайт и документов используйте отдельные бот, домен, ключи и БД: [приёмочная среда](qa/acceptance-environment.md). Нужен синтетический каталог. Настройки: [окружение](configuration.md); инструментальные способы отладки: [Telegram QA](../tools/telegram-qa/README.md).

В обычной среде `TELEGRAM_TEST_ENVIRONMENT=0` и HTTPS. Значение `1` в `app.bot.make_bot()` выбирает тестовый Bot API и разрешает HTTP-адрес Mini App для отдельного тестового бота. Это не режим обхода авторизации рабочего бота; ему также нужны отдельные аккаунт, подписи и QA-среда.

## Ручная проверка перед выпуском

Фиксируйте SHA/версию приложения, браузер/Telegram и ОС, тестовые роли и конкретный результат. [Чек-лист](qa/miniapp-acceptance.md) содержит критерии; [ROADMAP](../ROADMAP.md) — оставшиеся задачи.

- Telegram iOS, Android и Desktop: меню бота/inline-запуск, подпись `initData`, темы, клавиатура, safe area, фото, загрузка DOCX и исторического PDF, возврат в приложение.
- Клиент: оформление, ошибки доступности, повторная отправка, анкета, запрос изменения с причиной, одобрение/отказ, исправление и повторное подтверждение.
- Сотрудник: независимые роли и PII-доступ, проверка документов, закрепление, подготовка, выдача, возврат, конфликты и восстановление после обрыва сети.
- Получатели: доставка и редактирование карточки, отсутствие дублей, тихие часы/SLA; Google Calendar — защищённая подписка и фактическая задержка обновления.
- Пользовательские сессии: самостоятельность выполнения задач, понятность ошибок, крупный текст и управление клавиатурой. Проверка VoiceOver/TalkBack исключена из текущего согласованного объёма; полное соответствие WCAG не заявляется.

PASS присваивается только проверенным случаям. Синтетический Chromium/WebKit, smoke `/health`, реальный Telegram и наблюдение за пользователями являются разными доказательствами. Исторические протоколы не переносят PASS на новые версии автоматически.
