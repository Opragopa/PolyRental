# Стратегия тестирования PolyRental

Актуальные критерии и доказательства: [единый чек-лист Mini App](qa/miniapp-acceptance.md), [сессии на устройствах](qa/miniapp-device-session-2026-11-01.md). Production — 0.4.6; серверный набор — 255 тестов. Браузерные сценарии выполняются в Linux Chromium/WebKit. Проверки backup/restore — только в db_test. Ниже сохранена методика с историческими примерами; актуальные правила продукта и статусы приёмки определяются чек-листом и requirements.md.

> Фактический запуск инструментов, исправления и ограничения от 26 октября 2026 года описаны в [отчёте об отладке](telegram-debug-report.md). Ниже сохранена исходная методика, адаптированная 25 октября; статусы «не внедрено» относятся к тому проходу.

Адаптировано 25 октября 2026 года по исходному коду проекта и документации инструментов. Цель — проверить, что клиент может самостоятельно оформить аренду, а сотрудники — подготовить, выдать и принять оборудование. Это план проверок; он не является отчётом об их прохождении.

## Что меняется в исходном плане

| Предложение | Решение для текущего проекта |
|---|---|
| Vite и `npm run dev` как первый этап | Сейчас FastAPI раздаёт HTML/CSS/обычный JavaScript из `app/miniapp_static`. `package.json` и Vite отсутствуют. Начинать с существующего `/miniapp?preview=1`. |
| `telegram-mock-init-data` для бэкенда | Использовать pytest и существующий `signed_init_data()` в `tests/test_miniapp.py`. Node.js не нужен для Python API. |
| Обязательные отдельные этапы с двумя эмуляторами | Выбрать один инструмент для Telegram API и событий. Несколько рамок не дают независимого подтверждения работы реального клиента. |
| Любой запуск должен иметь подписанный `initData` | Разделить запуск через меню/inline-кнопку и кнопку клавиатуры: второй сценарий использует `sendData`, и пустой `initData` может быть нормальным. |
| `channel_id` обязательно приходит в `start_param` | Ссылки `booking_ID` открывают доступную пользователю заявку. Произвольный параметр канала не должен ломать запуск; маршрутизация по каналу не согласована. |
| `expand()` включает полный экран | Проверять разворачивание Mini App; полноэкранный режим — отдельная возможность, которую приложение сейчас не вызывает. |
| HTTP в тестовом Telegram работает сразу | Нужна отдельная настройка проекта: сейчас `miniapp_url()` отклоняет HTTP, а `make_bot()` не выбирает тестовый Bot API. |
| Работа в рамке подтверждает удобство | Дополнить реальные устройства наблюдением за пользователями и измеримыми критериями выполнения задач. |

Различия способов запуска и `expand()` описаны в [Telegram Mini Apps API](https://core.telegram.org/bots/webapps).

## Подготовка среды

Для интерфейса можно использовать уже работающий локальный сервис. Если он не запущен, запуск из корня проекта:

```powershell
docker compose -f compose.yaml -f compose.miniapp.yaml up -d --build db miniapp
```

Открыть `http://localhost:8000/health` и `http://localhost:8000/miniapp?preview=1`. Порт 8000 должен быть свободен; если его занимает другой режим проекта, сначала согласовать, какой сервис используется для проверки.

Этот запуск использует БД приложения `polyrental`, а не изолированную тестовую БД. Сам preview не отправляет заявки и показывает встроенные примеры каталога. Любые проверки реальной отправки, документов и управления выполнять в отдельном QA-развёртывании с тестовыми данными и тестовым ботом.

Для автоматических тестов отдельная БД уже предусмотрена в Compose:

```powershell
docker compose --profile test run --rm --build test
```

`tests/conftest.py` разрешает тесты только для БД с именем `polyrental_test` и очищает её таблицы перед каждым тестом. Не перенаправлять тесты на рабочую БД. В образе используется Python 3.12 и зависимости из `requirements.txt`.

## Этап 1. Быстрая проверка в браузере

Проверить ширины 320, 390 и 768 CSS-пикселей, затем обычное окно Desktop. В preview пройти путь «Сроки → Оборудование → Контакты → Проверка заказа».

| Сценарий | Ожидаемый результат |
|---|---|
| Пустые даты, выдача в прошлом, возврат раньше выдачи | Ошибка рядом с соответствующим полем; понятно, что исправить |
| Нулевой выбор оборудования | Нельзя перейти к контактам, показана понятная подсказка |
| Изменение сроков после выбора | Доступность и выбор пересматриваются, старый расчёт не подтверждается молча |
| Количество и итог | Видны количество и сроки по МСК; аренда бесплатная, суммы к оплате нет |
| Возврат на предыдущий шаг | Введённые значения сохраняются там, где это ожидается |
| Перезагрузка страницы | Восстанавливается черновик сроков и количества. Имя и контакт сохраняются с пояснением пользователю; паспортные поля в localStorage не сохраняются |
| Финальное подтверждение в preview | Показано сообщение о демонстрации; заявка не создаётся |
| «Ваши заявки» в preview | Понятное объяснение отсутствия реальных заявок |
| Запуск `/miniapp` без Telegram и без preview | Понятная инструкция открыть бота; отправка недоступна |
| Узкий экран и увеличение текста | Нет горизонтальной прокрутки страницы, обрезанных подписей и перекрытых действий |

Preview не подтверждает авторизацию, серверную доступность оборудования, работу документов или нативных кнопок Telegram.

Цвета интерфейса уже берутся из CSS-переменных `--tg-theme-*`. Обработчик `themeChanged` обновляет тему приложения; безопасные отступы учитывают CSS-переменные Telegram. В браузере без Telegram переключение темы ОС не заменяет проверку темы клиента. Проверить также фиксированные цвета ошибок и успешных состояний.

Критерий: все шаги доступны на узком экране; ошибки объясняют следующее действие; демонстрационный режим явно обозначен.

## Этап 2. API, подпись и бизнес-правила

Заголовок авторизации — `X-Telegram-Init-Data`, переменная бэкенда — `BOT_TOKEN`. Простой контрольный запрос для валидной подписи: `GET /api/miniapp/me`, ответ `200` с полями `id`, `admin`, `pii_admin`. При невалидных данных ожидается `401` и `detail: "Откройте приложение через Telegram ещё раз"`.

Верификатор `verify_init_data()` использует HMAC-SHA256 и `TELEGRAM_AUTH_MAX_AGE` (по умолчанию 86400 секунд), отклоняет дату в будущем, дубликаты ключей и некорректный ID пользователя.

| Проверка | Как построить входные данные | Ожидание |
|---|---|---|
| Валидный пользователь | Подписать тестовым токеном | `/me`: `200`, правильный ID и роли |
| Истёкший срок | Установить старый `auth_date` **до подписи**, старше настроенного лимита | `401`; тестируется срок, а не повреждение HMAC |
| Подмена пользователя | Изменить `user.id` **после подписи**, сохранить прежний `hash` | `401` |
| Другой бот | Подписать другим тестовым токеном | `401` |
| Повреждённый или отсутствующий hash | Изменить/удалить поле | `401` |
| Пустые данные, дубликаты, неверный JSON, дата в будущем | Сформировать отдельные случаи; для проверки структуры подписать согласованные поля | `401` |
| Клиент обращается к управлению | Валидная подпись обычного клиента | `403` |
| Сотрудник без PII-доступа запрашивает документы | ID из `ADMIN_IDS`, отсутствующий в `PII_ADMIN_IDS` | `403` |
| Другой клиент обращается к чужой анкете или отмене | Подпись другого клиента | `404`, чужие данные не раскрываются |

Для тестов срока фиксировать время, чтобы граничные значения не зависели от скорости выполнения. Наличие `hash` в панели само по себе не подтверждает принятие подписи сервером.

Существующее покрытие по исходникам:

- `test_signature_and_catalog_hides_serial`: валидная и просроченная подпись, отсутствие серийников в клиентском ответе.
- `test_api_roles_owner_isolation_and_private_cache` и `test_all_admin_api_routes_require_staff`: роли, изоляция клиентов и ограничения служебных маршрутов.
- `test_parallel_http_retry_only_notifies_once`: параллельный повтор HTTP-запроса и однократное уведомление.
- `tests/test_integration.py`, `tests/test_regressions.py`, `tests/test_miniapp.py`, `tests/test_bot_web.py`: аренда, комплектация, документы и резервный сценарий бота.

Доработка покрытия: отдельные негативные тесты HMAC и API-ответов из таблицы, границы срока, а также обработчик `web_app_data` с повтором и недоверенными полями. Наличие общего подписывающего helper не заменяет независимый контрольный пример подписи.

Критерий: проходят существующий набор и добавленные проверки; повтор запроса не создаёт вторую заявку, конфликт оборудования возвращает понятную ошибку, клиент не получает служебные или чужие данные. Три теста подписи не являются гарантией безопасности всего приложения.

## Этап 3. Интеграция с Telegram в эмуляторе

Базовый кандидат для текущего стека — [TMA DevKit](https://github.com/Deus-org/tma-devkit): у него документирован CLI для любого фреймворка, сценарии платформ и инспектор событий. В отдельной локальной QA-среде команда-кандидат:

```powershell
npx tma-devkit dev --app http://localhost:8000/miniapp
```

По README панель запускается на порту 5188. Это инструкция для последующего пилота, а не подтверждение совместимости с PolyRental: инструмент в рамках адаптации не устанавливался и не запускался. После успешного пилота зафиксировать версию и фактический способ подключения SDK.

Сначала проверить, что mock установлен до выполнения `app.js`, и что `/api/miniapp/me` принимает его подпись. В QA-среде токен подписания должен совпадать с `BOT_TOKEN` бэкенда. Использовать отдельный тестовый токен; не добавлять его в HTML, Git или публикуемые настройки панели. Приложение сохраняет ссылку на `window.Telegram.WebApp` при старте, поэтому замена объекта после загрузки и смена пользователя без перезагрузки могут оставить старое состояние роли.

Если CLI не обеспечивает нужный порядок загрузки, сначала подготовить отдельный локальный QA-вход со скриптом эмулятора перед `app.js`. Не считать такую интеграцию уже имеющейся. Не подключать одновременно два mock SDK.

| Сценарий | Проверка PolyRental |
|---|---|
| Запуск с валидным `initData` | Имя подставляется, `/me` возвращает роль, клиент видит свои заявки |
| Клиент, складской сотрудник, проверяющий документы | Кнопки и доступ соответствуют `ADMIN_IDS`/`PII_ADMIN_IDS`; после смены ID перезагрузить приложение |
| Нативные кнопки | MainButton меняет текст по шагам, блокируется при отправке; BackButton появляется на промежуточных шагах и возвращает без потери данных |
| Смена темы | Фон, текст, формы, ошибки и модальные окна читаемы; повторить в реальном клиенте |
| События | `ready`/`expand` при запуске, настройка и нажатия кнопок в соответствующих шагах; открытие списка само по себе не обязано повторно вызывать `ready` |
| Успех и ошибка HTTP-бронирования | Вызовы `HapticFeedback.notificationOccurred("success"/"error")`; аппаратную вибрацию проверить на телефоне |
| Дополнительный `start_param` | Обычный сценарий не ломается; ссылка booking_ID открывает разрешённую заявку; специального поведения по каналу нет |
| Потеря сети и конфликт доступности | Понятная ошибка, снятие блокировки отправки, возможность повторить действие без дубля |

`launchSource` — настройка конкретного эмулятора, а не поле, которое обязан читать PolyRental. Premium-статус сейчас не меняет роли и права приложения.

Другие инструменты из исходного плана:

- [vite-plugin-telegram-mini-app](https://github.com/tehfreak/vite-plugin-telegram-mini-app) существует, но требует Vite. Его `TELEGRAM_BOT_TOKEN` отличается по имени от проектного `BOT_TOKEN`; менять стек ради этого этапа не требуется.
- [telegram-mock-init-data](https://github.com/Tinkerbells/telegram-mock-init-data) генерирует подписанные launch-параметры. Если использовать позже, извлекать вложенный `tgWebAppData`, а не передавать весь набор launch-параметров как `initData`.
- [TMA-Studio](https://github.com/erfanmola/TMA-Studio) можно пилотировать как альтернативу DevKit. Эмуляция оформления Android/iOS не подтверждает поведение соответствующего WebView.
- `tg-mini-app-emulator` оставить дополнительным кандидатом: первичную документацию пакета и профиль `channel_inline` в этой проверке подтвердить не удалось. Команды, покрытие API и передачу `sendData` необходимо проверить перед включением в обязательную инструкцию.

Критерий: пилот выбранного инструмента воспроизводим, API принимает подпись, кнопки и события работают в перечисленных сценариях. Ограничения mock явно зафиксированы.

## Этап 4. Реальный Telegram

Основной маршрут — отдельный QA-бот и HTTPS-адрес QA-развёртывания. Для настройки публикации использовать раздел README «Публикация через Nginx». Минимальная матрица: реальный Android, реальный iOS и Telegram Desktop с записью версии клиента и ОС.

Обязательно проверить два разных пути:

1. **Меню бота / inline-кнопка `web_app`:** подписанный `initData`, HTTP API, создание заявки, список своих заявок, отмена, согласие и анкета; для сотрудников — управление и доступ к документам.
2. **Кнопка клавиатуры «Забронировать»:** возможен пустой `initData`; приложение передаёт `sendData`, бот берёт ID из `message.from_user.id`. Проверить получение номера заявки в чате и повторную серверную проверку цены/доступности. В этом режиме список заявок внутри Mini App направляет пользователя в чат.

Нельзя считать эмулированный вызов `sendData` доказательством доставки настоящего Telegram Update. По исходникам проект использует polling; готового webhook для подключения эмулятора не предусмотрено.

На устройствах дополнительно проверить системную клавиатуру, выбор и загрузку фотографий, просмотр документов, безопасные отступы, увеличение текста, сворачивание и повторное открытие приложения, восстановление сети и смену темы. Проверить, что возврат из фона обновляет список заявок, а кнопки доступны без перекрытия клавиатурой. Свайп назад включать в обязательные критерии только после определения ожидаемого поведения на конкретной платформе.

### Дополнительная ветка: тестовый сервер Telegram и HTTP

[Официальная инструкция Telegram](https://core.telegram.org/bots/webapps#using-bots-in-the-test-environment) разрешает HTTP в отдельной тестовой среде. Нужны отдельные аккаунт и бот; Bot API использует путь `/bot<token>/test/METHOD_NAME`.

Для текущего PolyRental эта ветка **пока требует реализации и настройки**:

- `app/bot.py:make_bot()` создаёт обычный Bot API client. Переключение на тестовый API должно применяться также к уведомлениям Mini App, использующим эту фабрику.
- `miniapp_url()` возвращает адрес только для HTTPS; `test_bot_entry_uses_https_only` закрепляет текущее поведение. HTTP можно разрешать только явным режимом тестового окружения с отдельными проверками.
- В `compose.miniapp.yaml` порт привязан к `127.0.0.1:8000`. Телефон не сможет обратиться к нему по LAN IP без отдельной QA-настройки публикации порта, доступности сети и брандмауэра.
- HTTP по LAN IP требует дополнительной проверки браузерных API: отправка использует `crypto.randomUUID()`, который требует [secure context по документации MDN](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID).

Поэтому смена URL в тестовом BotFather сама по себе недостаточна. До реализации этих пунктов использовать HTTPS-маршрут.

## Этап 5. Проверка удобства пользователями

Автоматические проверки v0.3.1 выполняются отдельно от сессий с пользователями:

```sh
docker compose --profile test run --rm --build test
node --test tests/calendar.test.cjs
npm ci --prefix tools/browser-qa
tools/browser-qa/node_modules/.bin/playwright install --with-deps chromium webkit
NODE_PATH=./tools/browser-qa/node_modules node tests/calendar-ui.cjs
NODE_PATH=./tools/browser-qa/node_modules PLAYWRIGHT_BROWSER=webkit node tests/calendar-ui.cjs
NODE_PATH=./tools/browser-qa/node_modules node tests/request-review-ui.cjs
NODE_PATH=./tools/browser-qa/node_modules PLAYWRIGHT_BROWSER=webkit node tests/request-review-ui.cjs
docker compose --profile test run --rm -v "$PWD:/app" test python scripts/benchmark_documents.py --output artifacts/document-benchmark.json
```

В PowerShell после `npm ci` используйте `& ./tools/browser-qa/node_modules/.bin/playwright.cmd install chromium webkit`, затем `$env:NODE_PATH='./tools/browser-qa/node_modules'; node tests/calendar-ui.cjs`. Для установленного Chrome можно задать `$env:PLAYWRIGHT_CHANNEL='chrome'` вместо загрузки Chromium. Второй прогон: `$env:PLAYWRIGHT_BROWSER='webkit'; node tests/calendar-ui.cjs`. Для Docker bind mount в PowerShell используйте `-v "${PWD}:/app"`.

Browser suite работает с локальными файлами через перехват запросов: БД, бот, Интернет и production ему не нужны. Она проверяет 320×640, 360×640, 390×844 и 430×844 в обеих темах, размеры тач-целей, первый экран, переход месяца без изменения высоты, клавиатуру, выбор и сброс диапазона, время МСК при timezone устройства America/Los_Angeles, сохранение при навигации и отсутствие API-вызовов в preview. Фото проверяются на синтетических пропорциях 4000×200, 100×3000 и 120×120. Отдельный сценарий проверяет открытие управления по серверной роли и переход «Как клиент».

`tests/request-review-ui.cjs` отдельно проверяет компактные карточки, клавиатурное раскрытие, ревью внутри выбранной заявки, подписи полей, light/dark, отсутствие PII-запросов у обычного оператора, подтверждение/исправление, историю, истечение блокировки и поздние ответы при смене заявки. В PowerShell после настройки `NODE_PATH` запустите `node tests/request-review-ui.cjs` для каждого `PLAYWRIGHT_BROWSER`. Снимки календаря создаются только при заданном `QA_SCREENSHOTS` (путь к папке), чтобы повторный прогон не менял доказательства предыдущих выпусков.

В GitHub CI браузерная матрица работает в [официальном образе Playwright](https://playwright.dev/docs/docker) `mcr.microsoft.com/playwright:v1.62.1-noble`: браузеры и OS-зависимости уже установлены, npm-пакет берётся через `npm ci`. Tag образа должен совпадать с версией в `tools/browser-qa/package-lock.json`. Локальный запуск без контейнера по-прежнему требует установки браузеров и Linux-зависимостей.

Pytest проверяет подписанный Telegram ID, одинаковые роли в боте/API, fail-fast env, изоляцию заявок, бот/API-синхронизацию, идемпотентность и межарендный буфер. Документы проверяются моками, синтетическим OCR без ПД, таймаутом внутреннего провайдера, шифротекстом в БД, PII-доступом и сохранностью изображений при downgrade/upgrade миграции `20261026_07`.

`tests/test_v031.py` проверяет права и минимальный состав истории, порядок событий, совместимость активной блокировки и видимость истёкшей, отсутствие событий после отклонённых переходов, сохранение ручного решения и запрет доступа к ПД обычному оператору. Эти сценарии используют только отдельную PostgreSQL `polyrental_test`.

Реальные Telegram iOS/Android, экранные дикторы и измерение точности на разрешённом наборе фотографий остаются отдельными приёмочными проверками. Не используйте реальные документы в публичных скриншотах или CI-артефактах.

Провести короткие сессии с 3–5 представителями клиентов и отдельно со складским сотрудником и проверяющим документы. Это предварительная качественная проверка, не статистическое исследование. Дать задачи без подсказок по расположению кнопок:

| Роль | Задача |
|---|---|
| Клиент | Выбрать сроки и две позиции с разным количеством, подтвердить, что аренда бесплатная, и отправить заявку |
| Клиент | Найти созданную заявку, понять её статус и следующий шаг; отменить разрешённую к отмене заявку |
| Клиент | После подтверждения пройти согласие и анкету, исправить отмеченную ошибку |
| Склад | Найти заказ, назначить экземпляры, выполнить проверки и провести выдачу/возврат |
| Проверяющий документы | Найти анкету, запросить исправление, проверить повторную отправку и открыть документ |

Предлагаемые цели приёмки, которые нужно подтвердить на сессиях:

- Не менее 4 из 5 клиентов оформляют тестовую заявку самостоятельно; если участников меньше, фиксировать число успешных попыток без процентов.
- Время оформления типовой заявки — до 2 минут без учёта ожидания менеджера и заполнения документов; фиксировать фактическое время и причины задержек.
- Каждый участник правильно понимает бесплатность аренды, МСК, статус заявки и следующий шаг.
- Нет потери введённых данных при обычном возврате на шаг назад, дублей заявки при повторе запроса, недоступных основных кнопок или раскрытия чужих данных.
- Ошибки ввода и сети позволяют продолжить задачу без помощи тестировщика.

Тестировщик записывает устройство, способ запуска, задачу, результат, время, места затруднений и слова пользователя. Для дефекта нужны шаги воспроизведения, ожидаемый/фактический результат и снимок экрана без персональных данных.

## Решение о готовности

Для каждого сценария отмечать `PASS`, `FAIL`, `BLOCKED` или `NOT RUN`; работающая рамка и отсутствие ошибок консоли не заменяют прохождение задачи.

Выпуск блокируют: обход авторизации или ролей, утечка документов, неверная доступность, двойное бронирование, невозможность завершить основной пользовательский путь. Остальные дефекты оценивать по влиянию и воспроизводимости; результат проверок на каждом устройстве хранить отдельно.

Состояние первоначальной адаптации от 25 октября: только анализ исходников и документации. Последующая практическая отладка вынесена в [отдельный отчёт](telegram-debug-report.md), а команды запуска — в [инструкцию QA-инструментов](../tools/telegram-qa/README.md). Предыдущие результаты из `website-audit-report.md` относятся к описанному там проходу и не являются новым подтверждением.
