# Production 0.5.3 — запрос клиента на изменения

05.11.2026 установлен `polyrental-release:0.5.3-5809a310b172`.

## Поведение

- Клиент получает кнопку «Запросить изменения» после подтверждения заявки,
  если анкета отправлена или проверена (`submitted`/`verified`), а подготовка
  ещё не началась. Причина обязательна, до 2000 символов; пробелы не принимаются.
- До решения сроки, состав, статус `confirmed` и резерв остаются прежними.
  Подготовка и ручная комплектация блокируются сервером, а не только интерфейсом.
- Оператор читает причину и подтверждает либо отклоняет запрос. Может оставить
  необязательный комментарий клиенту. При одобрении заявка переходит в
  `needs_changes`: клиент исправляет даты/состав через существующий процесс,
  затем заявка возвращается в `pending` на повторное подтверждение и проверку
  доступности. При отказе заявка остаётся `confirmed`.
- Mini App/сайт и личный чат бота используют один сервис решений. История и
  штатные уведомления показывают запрос/решение; текст причины не попадает
  в аудит и уведомления. Причина и комментарий решения зашифрованы и удаляются
  вместе с остальными приватными комментариями по существующим правилам хранения.
- Отмена, возврат на доработку или изменение менеджером делают старый запрос
  неактуальным. Повторные нажатия идемпотентны, решение привязано к конкретному
  запросу. Запрос и начало подготовки сериализованы блокировкой строки заявки.
- Миграция `20261105_43` добавляет `customer_change_requests` и уникальный
  частичный индекс: не больше одного ожидающего решения запроса на заявку.

## Проверки

- Полный набор на финальном образе: **402 passed, 1 skipped**. Только отдельная
  БД `polyrental_test`; production-заявки для проверок не создавались.
- Новые серверные проверки: причины/этапы/анкета, владелец/роли, повторная
  отправка, конкурирующие решения, гонка с подготовкой, одобрение → исправление
  → повторное подтверждение, отказ, устаревшие запросы, отмена, шифрование,
  удаление причины по сроку хранения, HTTP и подтверждение причины в чате.
- Headless Edge: `customer-change-request-ui` прошёл на 320/390 px, включая
  отсутствие отправки с пустой причиной, решения оператора, сохранение
  исправлений и экранирование HTML. Также PASS: `history-support-pages-ui`
  и `user-names-ui`. Ответы этих сценариев синтетические.
- Старый общий `completion-ui` остановился на сценарии каталога, ожидающем
  кнопку «Новый артикул». Он не считается прошедшим. Редактирование после
  одобрения отдельно покрыто новым браузерным сценарием и серверными тестами.
- Оба публичных `/health` и локальный `/health` возвращают `ok`, `0.5.3`.
  Новый домен проверялся с валидным TLS через `curl --resolve` из-за кеша VPN.
  Новый API без авторизации возвращает 401. Схема production — `20261105_43`,
  частичный уникальный индекс присутствует.
- SHA-256 13 runtime-файлов совпал со снимком в обоих контейнерах; публичный
  `app.js` также совпал. Ошибок запуска и перезапусков нет в проверенном интервале.
- Окружение перед переключением совпало с действующим. Пересозданы только
  бот и Mini App; домен, БД, Redis и Nginx сохранены. Commit/push не выполнялись.
- Публикация 0.5.3 в канал не создавалась; список автоматических объявлений
  `app/assets/releases.json` не менялся. Ручная проверка реальным пользователем
  внутри Telegram не выполнялась.
