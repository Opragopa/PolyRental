## Краткий вывод

Найден один блокирующий дефект, который в точности соответствует полученному сообщению: после подготовки расписки интерфейс оставляет доступным запрос исправлений анкеты, хотя сервер требует сперва вернуть заявку из `Готова` в `Подготовка`. Пользователь с ролью администратора ПД при этом не может выполнить возврат сам. В результате заявка останавливается без понятного следующего действия.

Также найдены три дефекта прав доступа и рабочего потока: сотрудник без доступа к ПД может забрать обращение и не суметь ответить на него; тому же сотруднику может отображаться действие подписания выдачи, которое сервер отклонит; сценарий возврата заявки не покрывает проблемный переход в автотестах.

## P0 — блокирует выдачу

### AUD-001. Нельзя запросить исправления анкеты после фиксации получателя расписки

**Симптом:** при нажатии «Отклонить / исправить» отображается: «Получатель расписки зафиксирован. До выдачи верните заявку в подготовку для исправления». После этого нет прямого пути продолжить работу из текущего экрана.

**Воспроизведение:**

1. Довести заявку до статуса `Готова` — при этом подготовлена расписка и сохранён снимок получателя.
2. Открыть проверку анкеты и нажать «Отклонить / исправить».
3. Сервер вернёт указанную ошибку.

**Причина:** сервер намеренно запрещает изменение анкеты при существующем снимке расписки (`app/pii.py:475`). При этом интерфейс разрешает решение по анкете на статусе `ready` (`app/miniapp_static/app.js:1315`). Допустимый серверный переход существует — `ready → preparing` (`app/rental.py:1068`) — и кнопка «Вернуть на доработку» формируется в карточке заявки (`app/miniapp_static/app.js:1081`), но это не связано с ошибкой проверки анкеты.

**Немедленный обход:** сотрудник с ролью оператора/менеджера/администратора должен в карточке заявки выбрать «Вернуть на доработку» → «Подготовка», обязательно указав причину. Затем можно запросить исправления анкеты и заново подготовить расписку. Администратор ПД без роли сотрудника сделать это не может — см. AUD-002.

**Рекомендация:**

- на статусе `Готова`, если расписка уже сформирована, не показывать действие «Отклонить / исправить»;
- вместо него показывать объяснение и одно релевантное действие: «Вернуть в подготовку» для уполномоченного сотрудника или «Передайте заявку оператору для возврата в подготовку» для администратора ПД;
- после успешного возврата автоматически вернуть фокус к проверке анкеты и показать, что потребуется новая расписка.

**Критерий приёмки:** у сотрудника не возникает серверская ошибка при обычном пути исправления; из сообщения в интерфейсе доступно следующее разрешённое действие.

## P1 — высокий приоритет

### AUD-002. Администратор ПД получает блокирующее действие, но не может выполнить обязательный возврат заявки

**Симптом:** пользователь с правом проверять документы может открыть проверку анкеты и запросить исправления, но не может самостоятельно вернуть заявку из `Готова` в `Подготовка`.

**Причина:** проверка анкеты доступна роли `pii_admin` (`app/miniapp_static/app.js:1117`), а API возврата на доработку требует роль сотрудника (`app/miniapp.py:134`; `app/rental.py:1073`). В интерфейсе кнопка возврата помечена как доступная только менеджеру/администратору для такого пользователя (`app/miniapp_static/app.js:1082–1088`).

**Риск:** процесс зависит от ручной передачи задачи между двумя ролями, но интерфейс этого не сообщает и не создаёт задачу ответственному сотруднику.

**Рекомендация:** зафиксировать политику: либо администратор ПД лишь создаёт запрос на возврат, а оператор подтверждает его, либо роль проверки ПД получает ограниченное право вернуть только связанную с исправлением анкету заявку в подготовку. В обоих случаях отобразить владельца следующего шага и уведомить его.

### AUD-003. Сотрудник без доступа к ПД может забрать обращение клиента и не суметь на него ответить

**Симптом:** любой сотрудник может нажать «Взять обращение», но читать сообщения и отвечать разрешено только владельцу обращения с правом `pii_admin`.

**Причина:** API получения обращения требует лишь роль сотрудника (`app/miniapp.py:489`), и кнопка показывается всем (`app/miniapp_static/app.js:2081–2083`). Открытие сообщений, напротив, доступно только владельцу с правом работы с ПД (`app/miniapp_static/app.js:2085`).

**Риск:** обращение оказывается закреплено за человеком, который не видит его содержание и не может помочь клиенту; он при этом способен пометить его закрытым или передать дальше.

**Рекомендация:** разрешать захват и закрытие обращений только сотрудникам с доступом к ПД либо отделить безопасную очередь триажа от сообщений клиента. Добавить запрет закрытия без ответа/явной передачи и отображать допустимых получателей при передаче.

### AUD-004. Для администратора ПД может отображаться подписание выдачи, которое сервер отклонит

**Симптом:** у пользователя без полномочий доверенного сотрудника может появиться «Подписал: выдача» / «Отметить приём оборудования».

**Причина:** клиент показывает кнопку, когда `trusted_signer` не равен строго `false` (`app/miniapp_static/app.js:1789`); для роли без этого поля значение `undefined`, поэтому условие выполняется. Серверный API требует сотрудника (`app/miniapp.py:1716–1720`), а бизнес-логика требует роль доверенного подписанта (`app/handover.py:191–192`).

**Риск:** на критическом шаге выдачи пользователь получает отказ вместо действия, что создаёт задержку у стойки выдачи.

**Рекомендация:** отображать действие только при `state.role?.trusted_signer === true`; дополнительно в API возвращать понятное сообщение «Подтверждать бумажную подпись может только доверенный сотрудник».

## Пробелы в тестировании

Автотесты интерфейса успешно выполняются для базовых сценариев оформления, согласия с ПД, проверки заявки, профиля и поддержки. Но в них отсутствуют следующие проверки:

1. Запрос исправлений анкеты в статусе `Готова` после подготовки расписки: возврат в подготовку и повторное создание расписки.
2. Матрица прав для роли «только администратор ПД» на действия с заявкой.
3. Матрица прав поддержки: захват, чтение, ответ, передача и закрытие обращения для каждой роли.
4. Отсутствие кнопки бумажного подписания у пользователя без `trusted_signer`.

## Исторический план исправления — выполнен / заменён

1. **Сразу:** исправить AUD-001 и AUD-002 одной связной логикой возврата на доработку; это разблокирует текущую выдачу.
2. **Следующим хотфиксом:** исправить проверки видимости действий из AUD-003 и AUD-004.
3. **Перед выпуском:** добавить четыре перечисленных регрессионных сценария в браузерные тесты и проверку ролей на API.

## Ограничения аудита

Проверка проводилась по текущему коду версии 0.4.1 и локальным автотестам. Нужна отдельная ручная проверка в Telegram на iOS и Android: обработка ошибок, возврат на доработку и уведомление назначенного сотрудника.
